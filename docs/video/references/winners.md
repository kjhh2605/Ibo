관찰일: **2026-11-04**. 조사 범위는 영상 구성뿐이며 Street Fitting 저장소·현재 앱 화면은 보지 않았다.

## 자료와 관찰 방법

- 6편 모두 **2024 Google Gemini API Developer Competition 공식 수상작**이다. 수상 사실과 제출 영상 URL을 동시에 연결해 주는 1차 출처: [Google 공식 수상 발표, 2024-11-21](https://developers.googleblog.com/en/announcing-the-winners-of-the-gemini-api-developer-competition/).
- 6편의 YouTube 메타데이터(길이·조회수), 실제 영어 수동/자동 자막, 영상 파일을 확보했다. 전체 구간을 **0초부터 10초 간격**으로 프레임 샘플링했다. Trippy는 5초 간격, Jayu의 첫 시연·Outdraw의 기술 설명·ViddyScribe의 기술 설명은 3초 간격으로 추가 확인했다.
- 자막의 문장 시작 시각을 초 단위로 반올림해 아래 구간을 작성했다. **구간은 내용 챕터이며 프레임 단위 컷 편집표는 아니다.** 10초 간격 정지 프레임만으로 특정 전환 애니메이션이나 배속을 단정하지 않았다. 직접 확인하지 못한 효과는 ‘미확인’, 해석·권고는 **[추론]**으로 구분했다.
- ‘실제 시연’은 영상에서 사용자 입력·앱 결과·기기 조작이 보였다는 뜻이다. 편집 없는 실시간 처리나 백엔드 진위를 독립 검증했다는 뜻이 아니다.

- 표본 한계: 서로 다른 대회를 얕게 훑는 대신, 공식 수상 및 동일 제출 영상 연결을 확실히 검증할 수 있고 2–3분에 들어오는 6편을 깊게 봤다. **수상작이라는 사실은 영상 편집만으로 수상했다는 증거가 아니다.** 고조회수 표본도 아니며, 이 표본의 조회수는 1,264–22,214회다. 모두 같은 대회이므로 전체 해커톤에 대한 통계적 일반화는 하지 않는다.

### 화면·편집·증거

- **화면 구성:** 인물 풀프레임 오프닝→데스크톱 풀프레임. 시연 중에는 작업 창과 검은 로그 창을 함께 두고, 중요한 요청만 검은 띠+흰 글자+청록색 세로선으로 표시한다. 전편을 말자막으로 채우지는 않는다.
- **전환/효과:** 인물에서 녹화 화면, 앱에서 앱으로 장면 전환. 첫 브라우저 시연은 바탕화면→작은 창→커진 창으로 진행된다. 이것을 편집 줌인지 창 최대화인지 단정할 수 없다. 손 추적 선은 확실한 기술 오버레이다. 명시된 배속 표시는 샘플에서 확인하지 못했다.
- **AI·기술 깊이:** 모델 이름 로고 나열보다 ‘화면 분석→외부 메모리→다른 앱에 코드 작성’, ‘화면의 버튼 탐색→조작’이라는 구체적 동작에 해설을 붙인다. 별도의 긴 아키텍처 강의가 없다.
- **실시간성 한계:** 입력과 결과는 보이지만 여러 클립으로 편집돼 있으며 모든 대기 시간이 보존됐다고 확인하지 못했다.
- **빌릴 것 [추론]:** Street Fitting도 영어 음성 질의 자체를 들려 주고 같은 문구를 화면에 짧게 고정한 뒤 후보→선택으로 이어가자. ‘에이전트’라고 주장하기보다 질의에서 어떤 후보·도구 결과가 생겼는지 보여 주자. 모델 설명은 해당 결과가 나오는 순간에 넣자.
- **피할 것 [추론]:** 2:25 이후처럼 적용 사례를 다수 추가하면 하나의 문제 해결 이야기가 약해진다. 화면이 작은 제출 환경에서 터미널 텍스트는 읽히지 않으므로 코드/로그를 곧바로 기술력의 증거로 간주하지 말자. 과장된 ‘anything’, 검증 안 된 의료 주장 같은 범용 수사도 불필요하다.

### 화면·편집·증거

- **화면 구성:** 실제 집·실제 사람 중심. 앱은 좁은 세로 패널로 화면 좌측, 그 지시를 실행하는 사람은 우측의 넓은 영역에 배치한다. ‘입력→앱 지시→현실 행동’의 관계를 동시에 볼 수 있다.
- **자막/효과:** 노란 직사각형 바탕의 영어 자막을 하단에 지속 제공한다. 인물 이름도 노란 라벨, 대화는 흰색·파란색 메시지 말풍선. 우상단 대회/해시태그, 로고/도구 뱃지와 작은 원형 그래픽도 등장한다.
- **전환:** 인물 단독 장면, 앱+인물 분할, 개발자 설명으로 교차한다. 배속·스피드램프는 확인하지 못했다.
- **AI·기술 깊이:** 실제 사진에 기반한 개별 지시와 상황별 행동이 보인다. 기술 설명 자체는 API/TTS/FlutterFlow 로고에 치우치며 프롬프트 구조나 신뢰성 검증은 자세히 보이지 않는다.
- **빌릴 것 [추론]:** ‘주인공이 겪은 문제’를 얼굴 없는 일반 시장 B-roll보다 구체적으로 보여 주는 방식. Street Fitting에서는 동일 옷·동일 노점이 처음 발견, 검색 결과, 돌아온 장면에 반복돼야 한다. 사람과 앱을 동시에 보여 줄 때 실제 맥락이 강해진다. 영어 음성+영어 자막 원칙에도 적합하다.
- **피할 것 [추론]:** 본격 시연이 1:36에 시작하는 긴 도입은 현재의 데모 25% 심사와 무배포 상황에 맞지 않는다. 18초 도구 로고 구간도 복사하지 말자. 한 화면에 인물·앱·자막·브랜드·로고를 모두 넣으면 작은 화면의 가독성이 떨어진다.

## 공통 구조와 차이: 이 표본에서 실제로 반복되는 것

1. **AI의 입력을 보이고 결과를 읽거나 듣게 한다.** Jayu의 음성 요청→작업 창, Gaze Link의 키워드/문맥→완성 문장, Outdraw의 그림→AI 답, Vite Vere의 방 사진→지시, Trippy의 음성→여행 정보가 해당한다. ViddyScribe는 이 연결보다 제작 설명에 더 많이 투자한다.
2. **사용자/현장 장면을 앱 화면과 결합한다.** 모바일 수상작에서 손·사람·기기·환경은 장식이 아니라 사용 맥락의 증거다. 다만 실사 인물이 있다는 사실만으로 그가 실제 고객인지, 연기인지까지 확인할 수는 없다.
3. **기술 설명 위치는 단일 정답이 아니다.** Jayu/Gaze Link는 결과가 나올 때 설명하고, Outdraw는 한 사이클 후 13초, Vite Vere는 데모 전에 18초, ViddyScribe는 중후반을 길게 쓴다. 따라서 ‘수상작은 모두 마지막에 아키텍처 25초’라는 결론은 근거가 없다.
4. **가독성용 짧은 오버레이가 많다.** 요청·Context/Result·Calibration·HUMANS LOSE 같은 글자는 화면에서 봐야 할 것을 지정한다. 모델 이름만 여러 개 띄우는 것은 그와 다르다.
5. **앱 밖의 결과가 엔딩을 강하게 만든다 [추론].** Vite Vere의 정돈된 방, Gaze Link의 발화, Trippy의 실제 여행, Outdraw의 플레이어 반응처럼 사용자 상태의 변화가 결말이 된다. Street Fitting의 자연스러운 결말은 ‘노점에 돌아와 그 옷을 다시 찾음’이다.
6. **수상작에도 우리에게 부적절한 선택이 있다.** Vite Vere의 늦은 시연, Trippy의 9기능 나열, ViddyScribe의 긴 개발담을 그대로 따라 하지 않는다. 대회 채점 방식과 별도 체험 가능성에 따라 최적 구조는 다르다.
